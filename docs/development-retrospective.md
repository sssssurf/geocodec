# 开发历程：geocodec

本文记录 geocodec 从选题到交付的过程：为什么做、范围怎么定、哪里做错过、最后
怎么验证。

## 1. 选题：地点短码

一个地点在文本里有很多种短写法：救援电话里念的是 Plus Code，业余无线电日志里
写的是 Maidenhead 网格，旅行笔记里可能是一串 geohash，网页链接里是 `geo:`
URI，地图标注上是度分秒。它们的共同问题是：字符串短、格式多、边界不规则、很
容易在自由文本里被误认，而现有工具往往只支持其中一种。

geocodec 只做这一层：把这些短码统一解析成经纬度，在它们之间转换，给出单元边界
和邻居，并能从一句话里找出所有码。它不碰地址库、不联网、不做投影和测地线，
因此范围小、依赖少、容易验证。

## 2. 范围取舍：只保留记法层

开发早期也实现过 UTM 正反算、MGRS 编解码和 Vincenty 测地线。后来判断这些不
属于本项目：它们回答的是「两个点相距多远、在哪个网格」，而 geocodec 回答的是
「这个地点用短码怎么写、边界在哪、这句话里出现了哪些码」。前者 MoonBit 生态
里已有成熟的投影/测地线库，后者才是本项目要补的一层。

于是删掉了 `utm.mbt`、`mgrs.mbt`、`geodesy.mbt` 及其测试和 CLI 子命令，把范围
收缩到五类记法、覆盖、扫描和尺寸报告。删掉之后，项目的一句话变得清楚，也避免
把两种不同的工程问题混在一个库里。

## 3. 范围：五类记法 + 三个「高于编解码」的能力

保留下来的五类记法：

- Geohash（1–12 位）
- Open Location Code / Plus Codes（2–15 位，含 shorten/recover）
- Maidenhead locator（2–10 位）
- RFC 5870 `geo:` URI
- 度分秒（`°′″`、`d/m/s`、`:`、半球后缀）

在此之上只做三件与「短码」直接相关的事：

1. **边界与邻居**：每个码的单元矩形、8 个相邻单元。没有边界，码就只是一个
   字符串；有了边界，才能判断包含、相交、做索引。
2. **覆盖**：给定一个包围盒和精度，列出覆盖它的 geohash 单元，并带单元数上限。
3. **检索**：从一句话里找出所有码；给出一个码的地面尺寸和面积。

明确不做：UTM/MGRS、椭球测地线、基准转换（GCJ-02/BD-09）、地址查询、多边形
运算。这些要么是投影/测地线库的领域，要么需要数据库/网络，不属于「短码」。

## 4. 结构：一个包，按「值 → 记法 → 检索」分层

```text
geo_math.mbt        经度归一化、纬度裁剪、定点格式化
text.mbt            ASCII 处理、无异常十进制解析
latlng.mbt          LatLng、BoundingBox、反子午线包含
dms.mbt             度分秒
geohash.mbt         Geohash（含 cover）
pluscode.mbt        Open Location Code（含 neighbors）
maidenhead.mbt      Maidenhead
geouri.mbt          RFC 5870
parse.mbt           单字符串识别、自由文本扫描
code_info.mbt       地面尺寸/面积
location_format.mbt 记法名称
cmd/main/           CLI
```

依赖方向单一：`geo_math`/`text` 是最底层，`latlng` 不依赖任何记法，记法模块
只依赖 `latlng`，`parse` 依赖所有记法，`code_info` 依赖三种格网记法。没有循环
依赖，也没有「工具包」式的万能模块。

## 5. 关键决策与被否决的方案

### 5.1 Plus Codes：整数域，而不是逐位浮点

最直观的写法是按 20°、1°、0.05°…逐位加减浮点数。10 位之后单元只有 13.5 m，
15 位只有几厘米；浮点累加误差会和单元尺寸同一量级，编码后再解码可能偏移一个
单元。

最终按 OLC 规范采用整数域：纬度乘 `20^3 × 5^5 = 25,000,000`，经度乘
`20^3 × 4^5 = 8,192,000`，先转成 Int64，再做整除和取模。这样 15 位码的边界
完全由整数决定，浮点只在最后转回度数时出现一次。Int64 是必须的：纬度整数最大
到 45 亿，超过 32 位。

被否决的方案：用 `Float`（精度不够）、用字符串逐字符进位（能做但对 15 位很
啰嗦）、直接移植参考实现（验收要求说明来源，且没有必要）。

### 5.2 覆盖：先算数量，再生成

`geohash_cover` 不是「先枚举再截断」。它先算行数、列数，检查乘积是否超过
`max_cells`，超过就返回 `None`；生成阶段按「纬度升序、经度升序」输出。跨
180° 的盒子拆成两段经度列，避免得到一个从 -180 到 179 的假大盒子。

被否决的方案：递归四分（好写，但顺序不稳定，也不容易保证上限）、用 geohash
前缀裁剪（会漏掉边界单元）。

### 5.3 扫描：普通英文单词也是合法 geohash

`parse_codes` 的第一版直接对每个 token 调 `parse_location`。测试句子
「Meet at … near … or send … and …」返回了 7 个结果：除了 4 个真码，还把
"Meet" 和 "send" 当成了 geohash——它们确实只由 geohash 字母表里的字符组成，
长度也合法。

修正不是「加一个停用词表」（永远不全），而是把规则写清楚：扫描时，token 必须
同时含数字和字母，且 geohash 至少 5 位。所有真实记法都含数字；代价是极少数
全字母或全数字的 geohash 不会被扫描到——直接调用 `parse_location` 仍然接受。
这条取舍写进了 README 和测试，评审可以看到「为什么这样定」，而不是一个魔法。

### 5.4 反子午线：包围盒不能假设 `west <= east`

Geohash、Plus Code、Maidenhead 的单元都可能跨 180° 经线。`BoundingBox` 因此
允许 `west > east` 表示跨线，`contains` 分两种情况，`width` 用
`east + 360 - west`，中心点再归一化。包含判断加了 `1e-9` 度容差（约 0.1 mm），
只吸收浮点表示误差：Plus Code 解码会把角点 round 到 14 位小数，恰好落在单元
边上的点可能因为一个 ulp 被判定在外。

### 5.5 全函数：连数字解析都自己写

对外承诺「不抛异常、不 panic」，就不能在内部用会 raise 的 `parse_double`。
坐标文本不需要科学计数法，于是写了一个只接受 `[+-]?digits[.digits]` 的解析器：
逐字符、显式返回 `Option`。这样 `parse_dms("1e999")`、`geo:0,0;u=1e999` 都是
`None`，而不是依赖异常路径。所有编解码入口先检查长度、字符集和数值范围。

## 6. 测试策略：标准向量、闭环、属性、健壮性

四层测试抓不同的问题：

1. **标准向量。** `u4pruydqqvj`、`ezs42`、`849VCWC8+R9`、`8FVC9G8F+6X`、
   `IO91WM`，以及 10/11/15 位 Plus Code 的整数域闭环。它们保证「和别人算得
   一样」。
2. **闭环。** 每个记法、每个精度、两半球、日期变更线、极点。它们保证
   「自己前后一致」。
3. **属性测试。** 40 个确定性伪随机点过三种格网编解码；10 个随机盒子的 cover
   逐单元检查。它抓到过 Plus Code 的 grid place value 错误（见下）。
4. **健壮性。** 垃圾输入、超长输入、极值。它保证「坏输入不会变成崩溃」。

测试里也踩过「测试本身写错」的坑：最初把 Googleplex 的期望码写成
`849VCWC8+R9`，但输入用的是 `-122.0840`；实际规范示例用的是 `-122.08408`，
差 0.00008° 就让最后一个字符从 `9` 变成 `Q`。修正输入而不是修改实现，并在
测试里保留这个小数点，提醒后来者「码对输入敏感」。

## 7. 开发中真正抓到的三个 bug

1. **Plus Code 的 grid place value 用了随位数变化的值。** 第一版在解码 11–15
   位时用 `5^(n-1)`、`4^(n-1)` 作为起始 place，结果 11 位单元被算成一个点
   （宽高都是 4e-8 度）。闭环测试「每个长度都包含原点」直接失败。规范的做法
   是固定从 `5^4 = 625`、`4^4 = 256` 开始，每处理一位再除一次；位数少时只是
   提前结束，而不是换一个起点。
2. **删掉 MGRS 之前的 X 带高度。** 其他纬度带都是 8°，X 带是 72–84°N，十二
   度。第一版统一按 8° 算，80.2°N 的点反算成 8.2°N，误差 8,000 km；属性测试
   打印出这个点后才发现。虽然 MGRS 最后被删除，这个 bug 说明「属性测试比
   示例测试更容易抓边界」。
3. **扫描器把英文单词当地点码。** 见 5.3；测试从 7 个结果改成 4 个，并补了
   「不含数字的 token 不扫描」的规则。

## 8. AI 工具在开发中的角色

本项目在 AI 编程助手（DeepSeek Harness）辅助下完成。分工是明确的：

- **参赛者负责**：选题与范围、验收口径、
  标准与参考资料的取舍、每轮结果的复核与最终提交。
- **AI 负责**：按模块生成 MoonBit 初稿、测试与文档草稿；运行 `moon test`
  并根据失败信息定位问题；把标准中的公式转成代码。
- **质量闸门**：不是「AI 说对就对」，而是每个模块必须过标准向量和闭环测试；
  测试失败时先判断是代码错还是期望值错。上面三个 bug 都是测试先失败、再定位、
  再补回归测试。关键数值（OLC 10/11/15 位单元尺寸、geohash 已知码、Maidenhead
  伦敦码）都能在标准文档或公开示例里找到对照。

没有把参考实现的代码复制进来。OLC 的整数域、geohash 的交错位、Maidenhead 的
四级网格都是从规范独立写的；参考实现只用于核对行为和测试向量。

## 10. 已知边界与后续

- 只做 WGS84；不做基准转换（GCJ-02/BD-09 等）。
- 不做 UTM/MGRS、椭球测地线、距离/方位；需要这些请用专门的投影/测地线库。
- 不做地址查询、多边形、瓦片服务。
- 扫描器为了降低误报，要求 token 含数字；极少数全字母 geohash 不会被扫描到。
- `geohash_cover` 的上限是调用者给的；默认 1,000，超过返回 `None`。
- `BoundingBox` 是经纬度矩形，不是测地线包围盒；高纬度大范围时会偏大，这是
  「保守包含」的取舍。

## 11. 规模

- 库源码 1,947 行（不含测试），CLI 359 行，测试 581 行。
- 68 个公开函数，5 类记法，48 个测试块。
- 没有为了行数堆功能：每个记法只做「编码、解码、边界、校验」四件事，Geohash
  多一个 cover，Plus Code 多一个 shorten/recover 和 neighbors，三个记法共用
  `LatLng`/`BoundingBox`。

## 13. 一句话总结

这个项目把「一个地点可以有多种短写法」拆成值、记法、检索三层：用整数域解决
精度，用上限和边界规则解决覆盖，用「含数字」规则解决自由文本误报，用明确的
「不做」把投影和测地线留在库外。范围小、依赖少，每个记法都能用公开向量和闭环
测试验证。
